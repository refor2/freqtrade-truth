## Executive gate: matching values does not prove trade ownership

**Observed in the preview implementation:**

- `group_comparable_records()` in `core/reconciliation.py` links opposite-source records by
  exact canonical instrument, exact settlement currency, and close-time tolerance.
- `reconcile_group()` in `core/comparison.py` can return `MATCH` for one Freqtrade
  record and one or more exchange records if the selected numeric fields agree.
- `NormalizedTradeRecord` currently carries source-local `trade_ref`, not an authoritative
  cross-system execution/position linkage. The grouping code does not verify that references
  identify the same economic trade.
- `collect_funding_window_evidence()` intentionally returns **candidate** funding; it
  does not prove account, strategy, bot, or position ownership.

**Consequence:** Two independent closed trades on the same instrument/currency with nearby
timestamps and coincidentally equal values can be labeled `MATCH` under preview time-based
grouping. This is a *contract qualification gap*, not proof that the existing numerical
comparison algorithm is wrong.

**Proposed P0 rule, subject to #15 review:** A final **verified match** must require proven
cross-source ownership/identity and complete coverage of each field being claimed.
Time-only links must remain *candidates* or *unverified* rather than acquiring a misleading
verified financial status. Do not silently reinterpret the current `MATCH` enum: settle
the public vocabulary and migration policy first.

### Identity decision to resolve first

Proposed evidence ordering (not implementation):

1. **Verified strong link:** exchange order/execution/position identifiers shown by an auditable
   read-only source to belong to the same economic lifecycle as a bot trade.
2. **Verified bounded lifecycle:** only if a reviewed proof establishes exclusive ownership,
   start/end coverage, and absence of competing positions or external manual actions.
3. **Instrument, currency, timestamp and matching amounts:** candidate discovery only,
   explicitly insufficient for a final verified match.

A local Freqtrade `trade_id` and a Bybit `orderId` are different ID namespaces.
Matching the strings by accident does not establish linkage, and current Freqtrade read
adapter supplies no native exchange order-ID provenance. The final design must identify
the precise read-only source that can bridge this gap, or keep outcomes incomplete.

### Component arithmetic and double-counting

The public `docs/data-model.md` defines all values as **equity-signed**:
fees paid < 0, rebates > 0, funding paid < 0, funding received > 0.

For **independently sourced, non-overlapping** components with matching currency and
economic scope, the candidate accounting identity is:

`reconstructed_net = price_pnl + trading_fees + funding + other_adjustments`

Do not derive `price_pnl` by subtracting fees/funding from a field called
`reported_net_pnl` until the exchange explicitly verifies the reported-net inclusion
rules for this endpoint and lifecycle. In particular, Bybit inverse `closedPnl` is
already documented in `docs/bybit-adapter.md` as including fees and funding. Adding
those fees/funding to `closedPnl` again would double-count. Such reconstruction is
**not** done by the preview core.

Cross-currency PnL or fee conversion is **not** available in the preview; unsupported
currency pairs must remain non-comparable rather than be summed.

### Funding evidence is not attribution

`FundingEvidenceStatus.AVAILABLE` means candidate events were found in a fully declared
window and match the canonical instrument and settlement currency. It does **not**
prove attribution to a bot. `NO_EVENTS` means no event was present in the declared
complete source window, not that no funding could possibly have occurred outside an
incorrectly represented coverage period or on another account.

Before using an event for reported trade net, require an explicit owner/position linkage
or a separately reviewed exclusivity proof. Funding may span multiple timestamps,
and coincident timestamp/instrument alone is not enough.

## Security and architecture boundaries

Public, synthetic data only. No credentials, account/order identifiers from real
users, proprietary strategy logic, private operational details, or copied private
repository code. Remain GET-only, deterministic, immutable, and isolated from order
execution. Do not replace or couple to any private operator UI.

## 2026-10-21 #15-A implementation checkpoint — candidate evidence, not acceptance

The internal-only `adapters/order_link_review.py` introduces a deterministic, synthetic-data-tested
**candidate** lookup between explicitly positive-filled Freqtrade source order IDs and
exchange closed-PnL `trade_ref` order IDs. It rejects duplicate source records and invalid
fill classifications, excludes zero-filled/unknown-filled IDs, requires exact instrument and
declared settlement currency, and reports ambiguous ownership if order IDs are shared by
multiple bot snapshots or exchange records. Results deliberately use
`CANDIDATE`, `NO_CANDIDATE`, or `AMBIGUOUS`, never `MATCH`.

**Limitations:** Even an exact ID match is not verified account/position ownership, proof
of complete fills, complete financial ledger, or an authorized net-PnL reconciliation.
Callers must provide all potentially competing records; a missing competitor cannot be
inferred away. This isolated adapter helper is not re-exported as a stable public contract;
the existing `reconcile_group()` preview behavior and its known strict xfail are unchanged.
BOT OPS UI, exchange credentials, production, and trading are untouched.

**Next gate:** obtain and test authoritative account-scoped, exchange-side order/fill provenance
and complete position lifecycle coverage before #15 identity acceptance or private UI staging.
Issue #15 and the v0.1 release gate remain OPEN.

# v0.1 reconciliation contract review — decision record (PROPOSED)

**Status:** REVIEW ONLY / NOT ACCEPTED / NO RELEASE AUTHORIZATION  
**Scope:** issue [#15](https://github.com/refor2/freqtrade-truth/issues/15)  
**Source baseline:** `36a4bff021e81d72998857f4a9c9be5ec4d99d2d`  
**Date:** 2026-10-08

This document records the *current code behavior*, candidate decisions, and the evidence still
required before publishing stable v0.1 financial semantics. It does **not** approve or implement
attribution, rename statuses, change the public API, or unblock reporting. All scenarios below
are synthetic, not account observations.

## Executive gate: matching values does not prove trade ownership

**Observed in the preview implementation:**

- `group_comparable_records()` in `core/reconciliation.py` links opposite-source records by
  exact canonical instrument, exact settlement currency, and close-time tolerance.
- `reconcile_group()` in `core/comparison.py` can return `MATCH` for one Freqtrade
  record and one or more exchange records if the selected numeric fields agree.
- `NormalizedTradeRecord` currently carries source-local `trade_ref`, not an authoritative
  cross-system execution/position linkage. The grouping code does not verify that references
  identify the same economic trade.
- `collect_funding_window_evidence()` intentionally returns **candidate** funding; it
  does not prove account, strategy, bot, or position ownership.

**Consequence:** Two independent closed trades on the same instrument/currency with nearby
timestamps and coincidentally equal values can be labeled `MATCH` under preview time-based
grouping. This is a *contract qualification gap*, not proof that the existing numerical
comparison algorithm is wrong.

**Proposed P0 rule, subject to #15 review:** A final **verified match** must require proven
cross-source ownership/identity and complete coverage of each field being claimed.
Time-only links must remain *candidates* or *unverified* rather than acquiring a misleading
verified financial status. Do not silently reinterpret the current `MATCH` enum: settle
the public vocabulary and migration policy first.

### Identity decision to resolve first

Proposed evidence ordering (not implementation):

1. **Verified strong link:** exchange order/execution/position identifiers shown by an auditable
   read-only source to belong to the same economic lifecycle as a bot trade.
2. **Verified bounded lifecycle:** only if a reviewed proof establishes exclusive ownership,
   start/end coverage, and absence of competing positions or external manual actions.
3. **Instrument, currency, timestamp and matching amounts:** candidate discovery only,
   explicitly insufficient for a final verified match.

A local Freqtrade `trade_id` and a Bybit `orderId` are different ID namespaces.
Matching the strings by accident does not establish linkage, and current Freqtrade read
adapter supplies no native exchange order-ID provenance. The final design must identify
the precise read-only source that can bridge this gap, or keep outcomes incomplete.

### Component arithmetic and double-counting

The public `docs/data-model.md` defines all values as **equity-signed**:
fees paid < 0, rebates > 0, funding paid < 0, funding received > 0.

For **independently sourced, non-overlapping** components with matching currency and
economic scope, the candidate accounting identity is:

`reconstructed_net = price_pnl + trading_fees + funding + other_adjustments`

Do not derive `price_pnl` by subtracting fees/funding from a field called
`reported_net_pnl` until the exchange explicitly verifies the reported-net inclusion
rules for this endpoint and lifecycle. In particular, Bybit inverse `closedPnl` is
already documented in `docs/bybit-adapter.md` as including fees and funding. Adding
those fees/funding to `closedPnl` again would double-count. Such reconstruction is
**not** done by the preview core.

Cross-currency PnL or fee conversion is **not** available in the preview; unsupported
currency pairs must remain non-comparable rather than be summed.

### Funding evidence is not attribution

`FundingEvidenceStatus.AVAILABLE` means candidate events were found in a fully declared
window and match the canonical instrument and settlement currency. It does **not**
prove attribution to a bot. `NO_EVENTS` means no event was present in the declared
complete source window, not that no funding could possibly have occurred outside an
incorrectly represented coverage period or on another account.

Before using an event for reported trade net, require an explicit owner/position linkage
or a separately reviewed exclusivity proof. Funding may span multiple timestamps,
and coincident timestamp/instrument alone is not enough.

## Security and architecture boundaries

Public, synthetic data only. No credentials, account/order identifiers from real

execution. Do not replace or couple to any private operator UI.

## 2026-10-21 #15-A implementation checkpoint — candidate evidence, not acceptance

The internal-only `adapters/order_link_review.py` introduces a deterministic, synthetic-data-tested
**candidate** lookup between explicitly positive-filled Freqtrade source order IDs and
exchange closed-PnL `trade_ref` order IDs. It rejects duplicate source records and invalid
fill classifications, excludes zero-filled/unknown-filled IDs, requires exact instrument and
declared settlement currency, and reports ambiguous ownership if order IDs are shared by
multiple bot snapshots or exchange records. Results deliberately use
`CANDIDATE`, `NO_CANDIDATE`, or `AMBIGUOUS`, never `MATCH`.

**Limitations:** Even an exact ID match is not verified account/position ownership, proof
of complete fills, complete financial ledger, or an authorized net-PnL reconciliation.
Callers must provide all potentially competing records; a missing competitor cannot be
inferred away. This isolated adapter helper is not re-exported as a stable public contract;
the existing `reconcile_group()` preview behavior and its known strict xfail are unchanged.
private operator application, exchange credentials, production, and trading are untouched.

**Next gate:** obtain and test authoritative account-scoped, exchange-side order/fill provenance
and complete position lifecycle coverage before #15 identity acceptance or private UI staging.
Issue #15 and the v0.1 release gate remain OPEN.

## 2026-10-21 #15-A follow-up: provisional fee-ledger order candidates

Added internal-only `adapters/fee_ledger_link_review.py` on the isolated
[#22](https://github.com/refor2/freqtrade-truth/pull/22) candidate branch.
It combines validated positive-filled Freqtrade source order references with
the existing read-only Bybit transaction-log `order_ref`, but emits **only
candidate ledger event IDs**, not an attributed fee amount or a verified result.

- Accepts multiple distinct `TRADE` fee events for one order reference,
  because a single order can have multiple partial executions; it preserves
  all unique event IDs without aggregation or deduplication by order ID.
- Explicit `SETTLEMENT` and other non-`TRADE` events, including funding
  events containing an `orderId`, **are not fee candidates**. Same
  symbol/timestamp/order ID does not attribute settlement funding.
- Zero-filled and unknown-filled source orders never yield fee candidates.
  Competing observed order IDs, unknown/mismatched instrument or settlement
  currency, mixed funding in a TRADE record, missing trade fee, duplicate
  source records and multiple ledger sources fail closed or remain ambiguous.
- Candidate-only output cannot establish source/account scope, exhaustive
  pagination, position ownership, trade lifecycle coverage, completeness of
  the fee/funding components, or numeric net PnL. Ledger signs are preserved
  in read-only source records, and are not converted or subtracted from the
  already-net Bybit closed-PnL value.
- No `reconcile_group()` change, public stable export, private operator application wiring,
  trading execution, account read or production deployment.

Synthetic TDD regression cases exercise partial fills, settlement exclusion,
fee rebates, missing order references, competing bots, currency/instrument
conflicts, mixed components, duplicate events and deterministic input order.

**#15 identity/ledger attribution remains OPEN**. Next needed proof is a
complete read-only account-scoped order/fill/position lifecycle with exact
exchange provenance, verified ledger coverage and no competing activity.

Official source for TRADE versus SETTLEMENT and multi-execution order IDs:
https://bybit-exchange.github.io/docs/v5/account/transaction-log

## 2026-10-21 #15-C: bounded API pagination evidence (NO-LIVE)

The internal Bybit inverse transaction-log reader now has an additive
`fetch_paginated_window_evidence()` path. It reuses the existing complete
cursor traversal, duplicate-record rejection, request-window segmentation
and read-only transport, without changing `fetch()` or the public stable API.

It returns immutable **pagination evidence** only after the last cursor for
all requested 7-day subwindows is reached successfully; it explicitly rejects
`query.limit` (since `fetch()` would return a truncated record subset),
and submillisecond query bounds (the Bybit API uses milliseconds). A repeated
cursor, malformed source data or other fetch exception cannot produce
completed evidence. The result records the native Bybit symbol, settlement
currency, source name, time window and returned event records.

**Evidence boundary:** pagination exhaustion is NOT a guarantee of Bybit
historical retention, completeness of account event history, correct key /
account scope, identity of a bot position, or allocation of fee/funding
events. It is insufficient for final `MATCH` or verified PnL; source
retention and ownership qualification stay OPEN under #15. Existing
`collect_funding_window_evidence()` remains *candidate-only* and no
automatic handoff to it was introduced.

During review a suggested change to the provisional Freqtrade order reader
was explicitly **discarded**: the standard `StdlibJsonTransport` already
parses JSON float tokens into `Decimal` (`parse_float=Decimal`), so
ordinary Freqtrade `filled` numeric values were already handled by that
transport. A locally tested fallback to Python `float` was not shipped
because it was outside the current typed transport contract. No live REST
query was performed.

## 2026-10-21 #15-A: Bybit execution-ID and ledger trade-ID corroboration (NO-LIVE)

Read-only, **candidate-only** additions on draft PR #22:

1. `adapters/bybit_execution_evidence.py` invokes exactly
   `GET /v5/execution/list` using `category=inverse`,
   `orderId`, `execType=Trade`, explicit millisecond UTC bounds and
   exhaustive cursor traversal. It splits ranges into bounded, contiguous
   <=7-day subwindows. Returned `orderId`, `symbol`,
   `execType`, `execId`, positive `execQty`, `execTime`,
   optional `execFee` and optional `feeCurrency` are independently
   checked or preserved. One order may contain **multiple** separate
   `execId` fills; a duplicate `execId`, inconsistent response,
   incomplete pagination, unexpected timestamp, invalid quantity, non-Trade
   response or conflicting symbol fails closed. Source `execFee` is not
   aggregated or converted.
2. `adapters/execution_ledger_review.py` compares the returned
   `execId` **candidate** against a transaction-log `tradeId`
   **candidate**, requiring the same orderId, source identity, native symbol,
   settlement/fee currency and matched source fee (Bybit signed expense
   versus normalized equity-signed fee). It requires pagination-exhausted
   windows with time coverage and rejects duplicate IDs and competing,
   conflicting, missing or partially sourced values.
3. The module emits only existing provisional
   `OrderLinkReviewState` candidate/ambiguous/no-candidate records.
   There is **no new public export**, PnL equation, verified ownership,
   funding attribution, data mutation, trading operation or UI dependency.

**Evidence limit:** The Bybit documentation separately describes execution
`execId` and transaction-log `tradeId` but does not explicitly promise
that they represent the same namespace for all account modes or events.
Their equality and matching fee is therefore **supporting source-level
corroboration only**, not an accepted identity hierarchy or complete lifecycle.
`pagination_exhausted` is not a guarantee of retained history and
`feeCurrency` may be absent even for derivatives. A missing value stays
unknown, never zero or inferred BTC. Exact normalized Freqtrade-to-Bybit
account/position ownership remains unresolved under issue #15.

The official Bybit execution endpoint also states that **orderId filters
take precedence over symbol filters**. The reader validates every returned
record rather than trusting a symbol query filter.

### 2026-10-21 #15-A: fully synthetic three-source chain (still candidate-only)

The internal `review_bot_execution_ledger_candidates()` adds an explicit
**three-source candidate path** using:

1. positive-filled exchange order IDs observed in a closed Freqtrade trade
   detail (all competing bot snapshots must be provided together),
2. validated Bybit `orderId` -> multiple `execId` executions within an
   exhaustively traversed query window,
3. matching Bybit transaction-log `tradeId` / orderId / native fee records
   from an exhaustively traversed ledger window.

An explicit caller-supplied canonical `normalized_instrument` and
`settlement_currency` are required; Bybit native `BTCUSD` is **not**
automatically equated with Freqtrade `BTC/USD:BTC`. A competing observed
order ID, missing positive-filled order execution window, any uncorroborated
fill or mismatched fee results in **AMBIGUOUS**, not a fabricated candidate.
Zero/unknown-filled orders never produce a candidate. No gross/net PnL is
computed and no funding ledger entry is attributed.

**Important:** this is still NOT account, position or economic lifecycle
ownership proof. Source windows may not include retained history outside
their declared interval, external manual executions, missing alternative
trading accounts or all potential competing bot snapshots. A CANDIDATE
must not become `ReconciliationStatus.MATCH` or an authorized settlement
by itself. The documented `tradeId`/`execId` namespace link is not
explicitly guaranteed across all Bybit account modes. This code is not
wired into private private operator application and uses no real credentials.

### 2026-10-21 #15-A negative regression: no empty-window promotion

An additional three-source synthetic TDD case found that a bot trade with
**two positively filled order IDs** could be marked `CANDIDATE` if one
order had no returned execution events while the other had a matching
execution and fee ledger entry. This was reproduced RED before the fix.
The new fail-closed check requires **at least one execution record for
every positive-filled order ID** in the explicitly supplied source
windows; otherwise it returns `AMBIGUOUS` and no candidate record IDs.
It remains a candidate-only proof, never verified completeness of
historical order fills or a financial `MATCH`.

### 2026-10-21 #15-A explicit-zero ledger field correction

The legacy provisional `review_fee_ledger_order_candidates()` treated
a source-observed `funding=Decimal("0")` on a `TRADE` fee event as
mixed funding and therefore reported `AMBIGUOUS`, even when the fee
and positive-filled order ID matched. A synthetic RED regression
reproduced the overly strict behavior. The corrected validator accepts
`funding=None` (missing) or **exactly zero** as not contributing a
non-zero funding amount; **non-zero** funding mixed into a fee event
still fails closed. This does not attribute any funding value, prove
ledger completeness, or change reported net PnL.
